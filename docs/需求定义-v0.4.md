# AI-UK 智能提词器 · 需求定义

> v0.4 · 2026-08-09 · 状态：可进入 Phase 0 原生可行性验证；未通过验证前，不承诺完整 MVP。

## 0. 先定义问题

### 要解决的任务

老 K 在 iPhone 或 Mac 上录制中文口播时，需要一台**不依赖付费订阅、无需自建服务器、能让人专注念稿**的提词器。

完成任务不等于“实现语音识别”。用户应能完成以下闭环：

1. 粘贴一篇中文稿；
2. 看着摄像头预览念稿；
3. 文字会在说话时平滑前进、停顿时停住；
4. 停止后得到一条画面干净、音画同步的视频；
5. 在目标手机上连续录制时，不因过热、卡顿或错位而中断。

### 成功标准（P0 验收）

在事先指定的一台目标 iPhone、一个目标 macOS 版本和常温环境（22–26°C、未充电）上，用 600–1,500 字中文口播稿完成测试：

- 10 分钟录制不中断、应用不崩溃，成片可正常播放且音画同步；
- 停顿约 0.6 秒后，文字能稳定停住；恢复说话后能继续，不出现肉眼明显的跳跃或倒退；
- 试念者不需要每 10 秒手动纠偏一次；语音能力不可用时，能一键降级为手动提词并继续录制；
- 录制期间系统热状态不进入 `serious` 或 `critical`。若进入 `fair`，应用提示并可切换到低负载录制规格；
- 提词层只存在于预览，导出视频不含文字、按钮或半透明遮罩。

“手机不发烫”是体验愿望，不是可验证的需求；以上指标才是本项目的可验收替代。

## 1. 产品边界

### 已确定

| 项目 | 决定 |
|---|---|
| 使用者 | 老 K 个人使用 |
| 场景 | 录制中文口播，不做线下演讲或直播 |
| 平台 | iPhone 与 Mac 各可独立使用；开发和验收先 iPhone、后 Mac |
| 数据 | 讲稿、设置、成片默认只存本机；不做账号和自建后端 |
| 成片 | 干净原始口播画面，不烧录提词字幕 |
| 核心价值 | 语音跟随 + 稳定录制，而不是“功能最多的提词器” |

### 明确不做

- Android、账号体系、多人协作、云端稿库、直播推流；
- AI 生成讲稿、烧字幕、封面和 BGM；
- P0 中的外接麦克风/多机位/横竖屏自动重构；
- 为了“聪明”而让文字在低置信度时大幅跳行。

### 必须在 Phase 0 前填写的运行基线

| 字段 | 值 |
|---|---|
| 目标 iPhone 型号 / iOS | iPhone 15/16 系列，iOS 18+（待确认具体型号和版本） |
| 目标 Mac 型号 / macOS | MacBook Air 15（待确认 macOS 版本） |
| 最长单条录制时长 | 5 分钟 |
| 首选画幅 | 竖屏 9:16 |
| 最低可接受画质 | 1080p30 为主，720p30 为降级方案 |
| 是否允许语音数据经 Apple 服务联网识别 | 端侧优先；端侧不可用时可经 Apple 服务联网识别 |

**双端优先级**：iPhone 与 Mac 同步达到 P0（非先后关系）。Phase 0 的三个实验需在两台设备上分别验证。

## 2. 主流程和界面状态

不要把“开始”同时理解为预览、监听和录制。P0 用下面的四态流程：

```text
编辑稿件 → 拍摄准备 → 录制中 → 完成/保存
```

### 编辑稿件

- 首页首屏是大文本输入区，支持粘贴长文；
- 显示字数和预计时长（按可配置的默认语速估算）；
- 提供字体大小、文字透明度、初始速度、自动跟随开关；
- 最近一次未录完的草稿自动保留在本机。

### 拍摄准备

- 用户点击“开始录制”后，先请求尚未授权的相机、麦克风、语音识别和照片库/文件保存权限；
- 展示前置摄像头预览与提词层，允许确认构图；
- 3 秒倒计时后开始录制、语音检测和滚动；
- 权限缺失或设备不可用时，不进入假运行状态，明确显示原因和可行替代（例如仅手动提词）。

### 录制中

- 视频预览在底层，提词层在上层；提词层不写入视频文件；
- 当前阅读位置维持在屏幕中下部的固定“视线区”，文字从下向上经过该位置；
- 显示最少控制：停止、暂停/继续、自动/手动切换、速度加减；
- 发生来电、音频路由变化、存储不足、相机中断或热状态升级时，安全暂停并告诉用户能否继续。

### 完成/保存

- 停止即关闭采集并完成文件写入；
- iPhone 保存到照片库，Mac 弹出保存位置；
- 保存失败时保留临时文件并给出重试方式；
- 不自动删除原始视频。

## 3. P0 范围（按闭环而非功能数量）

### A. 稿件和提词显示

- 本机草稿、长文粘贴、中文标点分句和字数统计；
- 字体大小、行距、左右边距、文字/背景透明度可调；
- iPhone 使用响应式全屏布局；Mac 才支持可调整窗口尺寸。不要把“可拖拽窗口”错误地写成 iPhone 功能；
- 首次使用提供一套适合竖屏口播的默认值，设置在本机记忆。

### B. 录制和导出

- 前置摄像头 + 内置麦克风录制；P0 只承诺一个在目标机实测通过的画质规格；
- 先测 1080p30 与 720p30，默认采用通过热测试且满足成片质量的较低负载方案；
- 纵向方向、预览镜像和导出视频方向必须分别测试；预览可镜像，成片是否镜像须在测试前明确；
- 成片为 MP4/MOV 中任一在目标设备和剪辑链路可正常使用的格式，不承诺浏览器 WebM。

### C. 语音跟随（分层降级）

“听到声音就滚”与“听懂了稿子”是两种能力，不能混为一项需求。

1. **本地语音活动检测（VAD）**：检测持续说话与停顿，控制滚动启停。这是自动跟随的最低保障。
2. **语速估计**：以近期语音识别出的讲稿推进量估计速度，用限幅和平滑插值更新；不应每个识别结果都直接改变滚动速度。
3. **稿件重新锚定**：只在高置信度匹配时，将当前位置轻微拉回到讲稿附近的句子锚点。匹配失败时保持当前进度，绝不突然跳到远处。
4. **手动兜底**：自动模式不可用、识别偏差大或用户临场改稿时，保留速度加减、暂停和自动/手动切换。它属于 P0，不应推到 P1。

匹配策略：对讲稿做中文标点分句与文本归一化；在当前句前后有限窗口内做模糊匹配；只有超过阈值才重新锚定。重复词、口误、跳句、口语化改写和无识别结果都视为常态，不应造成大跳动。

### D. 可靠性与隐私

- 无网络、语音识别未授权、语音能力暂不可用时：保留录制与手动提词，不把“开始录制”整体禁用；
- 讲稿和视频不上传到自建服务，不做分析埋点；
- 若设备不支持端侧语音识别，且用户不允许联网识别，则自动跟随降级为 VAD 启停 + 手动速度，不暗中上传音频；
- 低存储、相机/麦克风权限拒绝、录制被系统中断、保存失败均需有可理解的提示和恢复路径。

## 4. 技术决策

### 产品实现路线

采用 **原生可行性验证 → iPhone MVP → Mac 适配**，而不是把浏览器原型当作核心技术风险的证据。

浏览器原型可用于验证文案输入和滚动视觉，但它不能证明原生相机管线、录制编码、音频复用、端侧识别或发热表现。因此它最多是可选的交互草图，不是阶段闸门。

### 建议架构

```text
SwiftUI 界面
 ├─ Prompt Engine：分句、当前位置、速度平滑、锚定
 ├─ Capture Service：一条相机/麦克风采集管线
 │   ├─ 写入原始音视频文件
 │   ├─ 输出音频样本给 VAD
 │   └─ 输出音频样本给 Speech（若可用）
 ├─ Speech Adapter：检查语言、授权、可用性和端侧能力
 └─ Storage / Permission / Thermal Monitor
```

- iOS 与 macOS 尽量共享 Prompt Engine、数据模型和 SwiftUI 视图；采集、权限、保存和窗口行为采用平台适配层；
- 不要同时启动两套竞争麦克风会话。Phase 0 必须验证“一条采集管线，音频同时供录制、VAD 和识别”的稳定性；
- `SFSpeechRecognizer` 的端侧能力必须运行时检查。`requiresOnDeviceRecognition` 不是“所有语言、所有设备必定离线”的承诺；
- 监测 `ProcessInfo.thermalState`。热状态升高时先提示，必要时停止自动锚定或建议切换低负载规格；
- P0 不引入服务器。这里的“不联网”是一个独立隐私决策：若选择允许 Apple 联网识别，须在产品中明确告知，而不是把“无自建服务器”误写成“永不出网”。

## 5. Phase 0：两天以内的原生风险验证

### 只做三个实验，不做完整 App

| 实验 | 方法 | 通过条件 | 失败后的决策 |
|---|---|---|---|
| 同时采集 | 前置相机+麦克风录制，同时取音频样本给 VAD/语音识别 | 连续 5 分钟有成片、音画同步、无采集冲突 | 先解决单管线或放弃”录制中全文识别” |
| 跟随手感 | 用 3 段真实中文口播稿，包含停顿、改口、跳句 | 停顿与恢复自然，无明显大跳 | 先保留 VAD 启停，削弱自动锚定目标 |
| 热与稳定 | 在目标 iPhone 用两种录制规格各录 5 分钟 | 不进入 serious/critical，回放正常 | 固化更低负载规格，或拆分录制与自动识别能力 |

### Phase 0 退出闸门

只有同时满足以下条件才进入完整 MVP：

- 实测设备可稳定同时录制和分析音频；
- 用户主观评分“跟得上且不干扰念稿”至少 7/10；
- 自动模式失败时，手动模式仍能完整录制；
- 已确定 P0 的默认画质、最长时长、联网政策和目标机型。

若端侧识别在目标设备上不支持或明显不够准，不把它伪装成可交付能力：P0 可以保留本地 VAD 自动启停 + 手动速度，全文对齐延后。

## 6. 后续阶段

| 阶段 | 交付物 | 退出标准 |
|---|---|---|
| Phase 0 | 原生技术试验与测试记录 | 通过上述四个闸门 |
| Phase 1 | iPhone + Mac P0 闭环 | 目标设备各完成 3 次真实口播录制 |
| Phase 2 | 稿库、导出规格、暗色模式、可选同步 | 不破坏 P0 稳定性 |
| Phase 3 | 持续打磨 | 无 |

双端同步 P0。Phase 1 需在 iPhone 和 Mac 上分别通过录制闭环验证，不拆分平台阶段。

讲稿库和设置记忆可在 iPhone P0 收尾时低成本加入；它们不是主要风险。外接麦克风、同步和多规格导出不应抢占语音跟随和热测试的时间。

## 7. 已知风险、证据与停止条件

| 结论/假设 | 当前状态 | 需要的证据 | 停止或降级条件 |
|---|---|---|---|
| 端侧中文识别可用且足够准 | 未验证 | 目标 iPhone 的实际识别/延迟测试 | 不支持或手感低于 7/10：不用它驱动全文对齐 |
| 同时录制+识别不会过热 | 未验证 | 两种规格各 5 分钟真机测试 | serious/critical 或成片异常：降规格或拆分能力 |
| 语音速度可稳定映射到滚动 | 合理推断 | 三段真实稿、含停顿和改口的录像 | 频繁跳动：只保留 VAD 启停和手动速度 |
| Mac 与 iPhone 可低成本共用 | 合理推断 | Phase 1 双端同步开发中的实际复用比例 | 平台差异过大：以共享核心、独立界面交付 |
| 免费 Apple 个人签名足够日常使用 | 有限制 | 实机安装流程 | 免费配置文件约 7 天失效；若嫌反复重装，评估付费开发者计划 |

## 8. 交给开发 agent 的执行约束

1. 先实现 Phase 0 的原生试验，不要先堆稿库、主题和动画；
2. 每一项能力都提供真实设备证据：日志、测试结果或可播放成片；模拟器不算；
3. 录制视频与 UI 覆层必须分离，成片不得包含提词文字；
4. 自动模式永远可以一键关闭，不能阻止手动录制；
5. 任何“本地识别”“不发热”“支持双端”的表述，都必须以目标设备的实测结果为准；
6. Phase 0 未通过时，先报告数据和建议的降级方案，不要用更多 UI 掩盖核心风险。

## 9. 开始开发前，用户只需确认四件事

1. 第一台验收 iPhone 的具体型号和 iOS 版本；
2. 常用画幅、最长录制时长，以及 720p30 与 1080p30 的最低质量底线；
3. 是否接受“端侧优先；端侧不可用时可选择 Apple 联网识别”，还是必须绝不联网；
4. Mac 是第二优先级适配，还是必须与 iPhone 同时达到 P0。

## 技术依据（供开发时核查）

- Apple 的 `SFSpeechRecognizer` 需要在运行时检查可用性；端侧识别仅在设备/语言支持时可用，且端侧准确度可能较低。
- `AVCaptureAudioDataOutput` 可从采集会话提供音频样本；应以此为依据验证录制与语音分析共用单一采集管线。
- iOS 可通过 `ProcessInfo.thermalState` 监测系统热状态并在状态升高时降低资源使用。
- 免费 Personal Team 可部署个人测试 App，但 iOS 配置文件会在约 7 天后失效，需要重新构建安装。
